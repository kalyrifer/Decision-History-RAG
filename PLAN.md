# Decision History RAG — итоговый пошаговый план реализации

Версия: август 2026.
Жёсткие ограничения проекта: **всё полностью бесплатно**, ноутбук без GPU, **никаких локальных генеративных LLM** (только API с бесплатными тарифами; разрешены небольшие CPU-модели для эмбеддингов/реранка), Windows + PowerShell.

---

## Как пользоваться этим документом

1. Каждая «Фаза N» — самостоятельное задание для ИИ-ассистента. Чтобы дать его нейросети: скопируй блок **«Универсальный контекст»** + целиком секцию нужной фазы. Этого достаточно, чтобы ассистент понял проект и делал фазу без остального документа.
2. Фаза считается закрытой только когда выполнены **все** пункты «Критерии приёмки». Не переходи к следующей фазе с непройденными пунктами.
3. Если ассистент предлагает библиотеку/сервис не из зафиксированного стека — отклоняй предложение (либо сначала осознанно обнови этот план).
4. Порядок работы с ассистентом внутри фазы: сначала проси список файлов, которые он собирается создать → потом реализацию по одному файлу → потом запуск проверок и вставку вывода обратно в диалог.

## Универсальный контекст (копировать перед каждой фазой)

> Проект: Decision History RAG — система, которая по вопросу вида «Почему выбрали X?» восстанавливает из истории GitHub-репозитория цепочку принятия решения: исходная проблема → рассмотренные альтернативы → аргументы → решение → имплементация (PR/commit) → текущее состояние. Ответ обязан содержать ссылки на конкретные issue/PR/commit на GitHub.
>
> Ключевой принцип архитектуры: связи между сущностями (issue↔PR↔commit↔files) — первоклассные данные с первой версии. Исходная проблема почти всегда лексически не пересекается с итоговым вопросом (issue про «нужен distributed cache» не содержит слова «Redis»), поэтому чистый hybrid-поиск до неё не добирается — нужен graph expansion по таблице связей. Ролевую разметку (problem/argument/decision) НЕ делаем на этапе ingestion — её выполняет LLM в момент синтеза над собранным подграфом.
>
> Среда: Windows 11, PowerShell, Python 3.11+, venv в корне проекта. Всё локально и бесплатно: никаких платных API и сервисов, никаких локальных генеративных LLM. Разрешены небольшие CPU-модели (sentence-transformers) для эмбеддингов и опционального реранка.
>
> Хранилище: PostgreSQL + pgvector — одна БД для метаданных, связей, full-text search и векторов.
>
> Запрещено: LangChain / LlamaIndex и подобные фреймворки; платные API; хардкод секретов в коде (только .env, .env не коммитится); эмбеддинг сырых диффов.

## Фаза 0 — Окружение, скелет проекта, золотой набор

**Цель:** рабочая среда и эталон для оценки — до первой строчки пайплайна.

**Задачи ассистенту:**
1. Создать структуру каталогов из раздела выше (без заглушек-модулей: только каталоги, .gitignore, README с одной строкой о проекте, requirements.txt с минимальным набором: httpx, GitPython, psycopg[binary], pgvector, sentence-transformers, pyyaml, python-dotenv).
2. docker-compose.yml с postgres:16 + pgvector; поднять контейнер; создать БД `decision_rag`.
3. Создать `.env.example` с перечнем ключей; попросить пользователя заполнить реальный `.env`: GitHub PAT (read-only, публичный доступ), ключ OpenRouter (openrouter.ai → Keys; бесплатно для моделей :free).
4. Помочь пользователю выбрать целевой **публичный** репозиторий: критерии — 1–5 тысяч issues, культура аргументации решений в issues/PR (не просто «merged»), пользователь знает домен. Записать выбор в config.py.
5. Вместе с пользователем собрать `eval/golden_set.yaml`: 8–12 вопросов вида «почему было принято решение X», для каждого вручную найденный правильный ответ и якорные сущности (номера issue/PR, SHA коммитов). Формат записи: вопрос; список ожидаемых якорных сущностей; краткий правильный ответ; ссылки-источники.
6. Скрипт-проверка окружения: читает .env, делает тестовый запрос к Postgres (проверка расширения vector) и к GitHub (`/rate_limit`).

**Критерии приёмки:**
- [ ] `docker ps` показывает запущенный Postgres; `\dx` показывает расширение `vector`.
- [ ] Проверочный скрипт: PG_DSN подключается, GH-токен валиден (200 от rate_limit).
- [ ] `golden_set.yaml` содержит ≥8 вопросов, у каждого есть якоря и источники.
- [ ] `.env.example` закоммичен, `.env` — в gitignore.

**Грабли:** приватный репозиторий брать нельзя — контент будет уходить в облачные бесплатные API. Torch-CPU скачивает колесо ~200 МБ — это нормально, не пытаться «облегчить» заменой на что-то экзотическое.

## Фаза 1 — Ingestion: git + GitHub API → сырые данные

**Вход:** Фаза 0 закрыта. **Результат фазы:** полные сырые данные репозитория на диске; выгрузка воспроизводима и докачиваемая.

**Задачи ассистенту:**
1. `git_source.py`: bare-клон целевого репо в `data/repo.git`. Извлечь по основной ветке: все коммиты (sha, author, date, message, список изменённых файлов со статусом A/M/D). Полные диффы НЕ сохранять — только пути + счётчики строк добавлений/удалений (полное тело диффа доставать лениво, по требованию, позже).
2. `github_source.py`: через GraphQL выгрузить issues и PR: номер, title, body, автор, createdAt/closedAt, state, mergedAt, labels, все комментарии (автор, дата, body), для PR — review-комментарии и итоговые ревью. Пагинация курсорами; бюджет points контролировать через встроенный объект `rateLimit { cost remaining resetAt }` в каждом запросе.
3. Через REST `/repos/{owner}/{repo}/issues/{n}/timeline` выгрузить события для каждого issue/PR: `cross-referenced`, `referenced`, `closed`, `connected`. Это главный будущий источник связей — сохранять события как есть.
4. Каждый ответ API дописывать в `data/raw/<тип>.jsonl`; прогресс писать в `ingest/checkpoints.json` (курсоры пагинации, последний обработанный номер/SHA). Повторный запуск продолжает, а не начинает заново.
5. Устойчивость: экспоненциальный бэкофф на 403/5xx, уважать `Retry-After`; логировать прогресс (обработано/осталось, скорость).

**Критерии приёмки:**
- [ ] Число issues и PR сходится с вкладками Issues/Pull requests на GitHub (±единицы за время выгрузки).
- [ ] Повторный запуск не перекачивает уже полученное (курсоры работают).
- [ ] В `data/raw` лежат jsonl по типам данных; суммарный размер — сотни МБ максимум.
- [ ] Лог завершения без необработанных ошибок API.

**Грабли:** squash-merge «теряет» оригинальные SHA коммитов PR в основной ветке — связь PR→commit берём из GitHub API в Фазе 2, не реконструируем по git log. Реакции и историю редактирований не выгружать — балласт.

## Фаза 2 — Нормализация и извлечение связей (мини-граф)

**Вход:** сырые данные Фазы 1. **Результат:** заполненная схема entities + relations в Postgres — фундамент всего поиска.

**Задачи ассистенту:**
1. `normalize/schema.sql`:
   - `entities(id PK, type CHECK IN ('commit','issue','pr','comment'), native_id, title, body, author, created_at, closed_at, state, url, extra JSONB)`; уникальность (type, native_id);
   - `relations(src_id FK, dst_id FK, kind CHECK IN ('closes','references','mentions','pr_commit','touches_file','parent'), source TEXT, meta JSONB, UNIQUE(src,dst,kind))`;
   - `files(entity_id FK, path)` — файлы commit/PR;
   - индексы: btree по (type, native_id), created_at; индексы на relations(src), relations(dst).
2. `parse_raw.py`: читает `data/raw/*.jsonl` → заполняет entities. Комментарии — отдельные сущности типа comment с relation kind=parent к своему issue/PR. Длинные body (>~1 МБ) обрезать с пометкой truncated в extra.
3. `extract_relations.py` — источники связей по убыванию надёжности:
   - события Timeline API (`cross-referenced`, `closed`, `connected`) → closes/references;
   - GitHub API: для каждого PR — список его коммитов (учитывая squash: ставить pr_commit и на исходные SHA, и на squash/merge SHA);
   - регулярки по телам текстов (`#123`, closes/fixes/resolves) — ТОЛЬКО fallback, помечать в поле source;
   - упоминания @user связями не считать (шум).
4. Отчёт-сверка: количество сущностей и связей по типам и источникам; выборочная ручная проверка связей по GitHub UI.

**Критерии приёмки:**
- [ ] Число сущностей = issues + PR + comments + commits (сверить с Фазой 1).
- [ ] Для 5 случайно взятых связей closes — подтверждение вручную на GitHub UI.
- [ ] Для 3 squash-merge PR связь pr_commit присутствует (пришла из API, а не из git log).
- [ ] Проверка целостности: нет висячих src/dst в relations.

**Грабли:** номера issue и PR пересекаются (это разные последовательности) — ключ обязан включать тип. Не классифицировать роли сообщений здесь — это задача Фазы 5.

## Фаза 3 — Представление и эмбеддинги

**Вход:** БД Фазы 2. **Результат:** каждый чанк имеет эмбеддинг и tsvector в той же БД.

**Задачи ассистенту:**
1. `represent/to_text.py`: шаблон текста для каждой сущности, например `[ISSUE #123 · 2021-04-03 · alice] Заголовок\nТело`; для комментария добавлять заголовок родителя (контекст треда); для коммита — сообщение + список файлов, НЕ diff. Тела длиннее ~1500 символов резать на чанки по абзацам с overlap ~150 символов; каждому чанку — ссылка на родительскую сущность (parent-document retrieval: ищем кусок, отдаём LLM родителя целиком).
2. Таблица `chunks(id PK, entity_id FK, idx INT, text TEXT, embedding vector(384), tsv tsvector GENERATED ALWAYS AS ... STORED)`; размерность вектора — под выбранную модель (384 для bge-small/e5-small). tsv — конфиг english, title с весом выше тела.
3. `represent/embed.py`: sentence-transformers bge-small-en-v1.5 на CPU, батчи ~32, нормализация векторов; для QUERY потом использовать префикс инструкции из карточки модели (у bge: «Represent this sentence for searching relevant passages: »; у e5: «query: » / «passage: ») — вынести префиксы в config. Идемпотентность: не переэмбеддивать существующие чанки; лог прогресса.
4. Индексы: HNSW по embedding (оператор cosine), GIN по tsv.

**Критерии приёмки:**
- [ ] count(chunks) соответствует ожидаемому (сущности, поместившиеся целиком + куски длинных).
- [ ] Санити-поиск: 5 ручных запросов возвращают осмысленные сущности в топ-5 — отдельно по FTS и отдельно по векторам.
- [ ] Время полного эмбеддинга измерено и записано в README (ориентир: минуты на тысячи чанков на CPU).
- [ ] Расход денег: 0.

**Грабли:** забыть query-префикс модели — качество поиска тихо падает на десятки процентов; несоответствие метрики расстояния нормализации векторов даёт мусор — использовать косинус и нормализованные векторы.

## Фаза 4 — Retrieval: гибрид + RRF + graph expansion

**Вход:** БД Фазы 3. **Результат:** функция `pipeline.search(query) -> evidence-set` (ранжированные сущности с типом, датой, score, числом хопов, URL) + CLI-режим печати результатов таблицей — главный инструмент отладки.

**Задачи ассистенту:**
1. `retrieve/hybrid.py`: два параллельных поиска top-25 — FTS (`websearch_to_tsquery`) и pgvector cosine top-25; слить Reciprocal Rank Fusion (k=60): итоговый score = сумма 1/(60+rank_i) по спискам, где сущность встретилась.
2. `retrieve/expand.py`: от якорей (топ-10 после fusion) пройти по relations в обе стороны на глубину ≤2 SQL recursive CTE; веса затухают ×0.5 за хоп; жёсткий лимит ~40 дополнительных сущностей; приоритет видов связей: closes > references > mentions > parent. Обязательна защита от циклов (visited-set в CTE).
3. Вместе с сущностью подтягивать её комментарии (parent-document); финальный сет группируется по «цепочке», внутри сортируется по timestamp.
4. `retrieve/pipeline.py` объединяет шаги; CLI: `python cli.py search "почему X"` печатает таблицу (score, hop, тип, заголовок, URL).
5. Опционально вторым заходом: реранк bge-reranker-base поверх расширенного множества; решение принять по цифрам Фазы 6, не по ощущениям.

**Критерии приёмки:**
- [ ] На ≥80% золотых вопросов правильная якорная сущность входит в топ-10 после fusion.
- [ ] Ключевой тест идеи: существует хотя бы один золотой вопрос, где исходная issue лексически далека от вопроса, и она появляется в выдаче ИМЕННО благодаря expansion (проверить отключением expand — она исчезает).
- [ ] Один поиск выполняется за секунды локально.

**Грабли:** expansion без лимитов взрывает объём — держать жёсткие лимиты глубины и количества; взаимные ссылки сущностей зацикливают наивный CTE.

## Фаза 5 — Синтез ответа (LLM по бесплатному API)

**Вход:** pipeline Фазы 4 + ключи из .env. **Результат:** команда `python cli.py ask "почему X"` выдаёт нарратив решения с цитатами и ссылками.

**Задачи ассистенту:**
1. `synthesize/llm.py`: единый интерфейс generate(prompt, max_tokens). Провайдер — OpenRouter; список рабочих моделей строится динамически из каталога (все с суффиксом `:free`, приоритет задать в config). Ретраи на 429/5xx с переключением на следующую модель (ротация решает дневные лимиты одной модели); таймауты; логирование расхода токенов. Низкая температура (≤0.2).
2. Сборка контекста в answer.py: блоки отсортированы по времени; формат блока: дата · тип · автор · URL · текст (длинные комментарии обрезать); суммарный бюджет ~40–60 тыс. символов; приоритет отбора: якоря и их соседи 1-го хопа.
3. `synthesize/prompt.py` — строгий шаблон выходного нарратива:
   1) Исходная проблема (со ссылкой);
   2) Рассмотренные альтернативы;
   3) Аргументы за/против (короткие цитаты с указанием автора и ссылки);
   4) Решение и кто его сформулировал (ссылка);
   5) Имплементация (PR/commit, ссылки);
   6) Что известно о текущем состоянии;
   7) Уверенность и чего не хватает.
   Явное правило в промпте: «Если цепочка не восстанавливается из приведённого материала — прямо скажи об этом. Не выдумывай факты и цитаты. Цитируй только ID/URL, присутствующие в контексте.»
4. Роль каждого сообщения (problem/argument/decision) определяет LLM в момент синтеза — никакой предварительной разметки чанков нет.
5. Вывод: ответ + список источников (URL, роль в цепочке) + мини-timeline ключевых событий с датами.
6. Обработать случай слабого evidence-set: честный отказ с подсказкой, как переформулировать запрос.

**Критерии приёмки:**
